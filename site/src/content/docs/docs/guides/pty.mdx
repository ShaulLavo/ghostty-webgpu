## Why binary frames matter

Set `socket.binaryType = 'arraybuffer'` before listening for messages:

- Incoming binary frames go straight into `terminal.write(new Uint8Array(data))`. `libghostty-vt` decodes UTF-8 incrementally, even when a 4-byte emoji or escape sequence arrives split across two WebSocket frames.
- Outgoing keystrokes and pastes from `terminal.onData(({ bytes }) => ...)` go back to the socket as binary frames without ever passing through `TextDecoder`.
- Text frames stay free for small JSON control messages such as `{ type: 'resize', columns, rows }`.

<Aside type='caution' title='Pitfall: server sending text frames'>
  If your server sends PTY stdout as WebSocket text frames instead of binary frames, `data
  instanceof ArrayBuffer` is `false` and the client ignores the output. Always send PTY bytes as
  binary frames so text frames remain unambiguous control messages.
</Aside>

## Keeping PTY dimensions synchronized

Because `await terminal.open(host)` fits the grid synchronously before resolving, `terminal.geometry()` already matches the host container's true columns and rows when the socket's `open` handler fires `sendSize()`. After that, `terminal.onResize` pushes updated `{ type: 'resize', columns, rows }` messages whenever the layout, DPR, or font size changes.

## Handling heavy streaming output

A fast compiler or `cat` on a multi-megabyte log can outpace the browser if your server writes unbounded chunks. Combine three controls when throughput matters:

- **Server-side backpressure:** Check `socket.bufferedAmount` before pushing more PTY bytes. Pause PTY reads once queued bytes cross your high-water mark and resume when the socket drains.
- **Client-side batching:** For bursty streams on the main thread, call `terminal.writeBatched(bytes)` instead of `terminal.write(bytes)` to coalesce writes across animation frames under a configurable byte budget (`writeQueue` option).
- **Direct worker ports:** On `ghostty-webgpu/worker`, transfer a producer's `MessagePort` directly to the terminal worker via `attachOutputPort(port)` and coordinate draining with `fenceOutput(sequence)` so bulk PTY bytes bypass the main thread altogether.

## Handling reconnects cleanly

Opening a fresh WebSocket needs an explicit session policy on the server:

- **New shell:** spawn a fresh PTY and call `terminal.reset()` on the client before streaming output so stale screen state from the previous session is cleared.
- **Reattaching to a persistent PTY:** replay the server's buffered history (or send a `SIGWINCH` redraw) into the existing terminal.

<Aside type='note' title='Saved viewports are visual only'>
  `captureViewport()` captures a lightweight visual snapshot for instant first paint, not live
  emulator state or shell scrollback. Always rely on your server's PTY or replay log to restore a
  live session.
</Aside>
