`ghostty-webgpu` ships four renderers against one `libghostty-vt` state: WebGPU, WebGL2, Canvas 2D (`canvas2d-pixels` and `canvas2d-fill-text`), and DOM.

## 1. Automatic selection and Canvas-first startup

<Code code={sample} lang='ts' title='renderers.ts' />

In the default `presentation: 'frame'` mode on the main entry:

1. `open()` starts with `CanvasTerminalRenderer` (`canvas2d-pixels`) so the first frame paints without waiting for GPU adapter and pipeline creation.
2. After the first Canvas frame reaches the compositor, `StartupTerminalRenderer` initializes the target GPU backend on a separate offscreen `<canvas>` element.
3. Once the GPU renderer draws its first matching frame (and no pointer gesture, link click, or DEC mode 2026 synchronized-output hold is active), the host swaps the painted GPU canvas into the DOM via `adoptCanvas` and disposes the temporary Canvas renderer.

Automatic GPU order depends on platform and presentation mode (defined in `src/render/shared/backend-order.ts`):

- **macOS, Windows, and mobile:** tries hardware WebGPU first, then WebGL2.
- **Desktop Linux, or `presentation: 'immediate'`:** tries WebGL2 first, then hardware WebGPU. Desktop Linux prefers WebGL2 because Chromium on Linux presented separate WebGPU canvases with higher CPU cost in benchmarks. `presentation: 'immediate'` prefers WebGL2 because only WebGL2 and Canvas 2D support `desynchronized` contexts.
- **Fallback chain:** automatic selection skips software WebGPU adapters. If neither GPU backend succeeds, the terminal stays on Canvas 2D; if Canvas 2D is unavailable, it falls back to `DomTerminalRenderer`.

Check `terminal.diagnostics.rendererBackend` at any time (`'canvas2d'`, `'webgl2'`, `'webgpu'`, or `'dom'`). Note that right after `open()` in `frame` mode it initially reports `'canvas2d'` until the background GPU handoff finishes.

## 2. Explicit renderer modes

Pass `rendererMode` to `Terminal.create()` on the main entry:

| `rendererMode`         | Behavior                                                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| `'auto'` (default)     | Canvas-first startup, then platform-ordered hardware GPU, then Canvas 2D, then DOM.                          |
| `'webgpu'`             | Canvas-first startup, then WebGPU (accepts any adapter, including software). Stays on Canvas if unavailable. |
| `'webgl2'`             | Canvas-first startup, then WebGL2. Stays on Canvas if unavailable.                                           |
| `'canvas2d-pixels'`    | Stays permanently on the WASM-composited pixel Canvas renderer (`canvas-compose.wasm`).                      |
| `'canvas2d-fill-text'` | Stays permanently on the `fillText` Canvas 2D renderer.                                                      |

Pass `presentation: 'immediate'` to skip Canvas-first startup and paint writes immediately (useful for low-latency single-terminal hosts, main entry only). Pass `rendererFactory` to construct a specific renderer class yourself (such as `DomTerminalRenderer`).

The worker entry (`ghostty-webgpu/worker`) has its own `backend` option: `'auto'`, `'webgpu'`, or `'webgl'`. See [Run in a worker](https://ghostty.shaulavo.dev/docs/guides/workers/).

## 3. Context and device loss recovery

- **WebGPU device loss:** `WebGpuTerminalRenderer` watches `device.lost`, acquires a fresh device lease, rebuilds atlas textures and pipelines, and repaints from the intact native `libghostty-vt` state.
- **WebGL2 context loss:** `FallbackTerminalRenderer` replaces the claimed `<canvas>` and advances through the remaining backend order (including hardware WebGPU on Linux when WebGL2 was chosen first, then Canvas 2D).

## Troubleshooting

### WebGPU is skipped on a machine with a GPU

WebGPU requires a secure context (`https://` or `localhost`) and a hardware adapter in `'auto'` mode. Software adapters (such as SwiftShader) are skipped unless you explicitly set `rendererMode: 'webgpu'`.

### Opening many terminals exhausts WebGL contexts

Browsers cap live WebGL contexts per page (typically 8 to 16). Dispose removed terminals promptly, or share GPU devices across terminals using `TerminalWorkerPool` on the worker entry.
