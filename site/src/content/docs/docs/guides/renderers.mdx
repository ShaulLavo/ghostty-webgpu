## 1. Let the terminal choose

<Code code={sample} lang='ts' title='renderers.ts' />

The main entry in frame presentation starts on Canvas 2D and switches to the GPU once it draws a frame. On desktop Linux, it tries WebGL2 before hardware WebGPU. On other platforms, it tries hardware WebGPU first. `diagnostics.rendererBackend` reports the renderer currently in use.

## 2. Choose Canvas 2D explicitly

Set `rendererMode` to `canvas2d-fill-text` when creating the main-thread terminal. The explicit `canvas2d-pixels` mode enables the pixel compositor.

Set `rendererMode` to `webgpu` or `webgl2` to try a specific GPU backend. The terminal keeps painting on Canvas if that backend is unavailable. `rendererFactory` lets the host supply its own renderer. The worker entry has a separate `backend` option with `auto`, `webgpu`, and `webgl`. [Worker guide](https://ghostty.shaulavo.dev/docs/guides/workers/)

## 3. Check the result

All four backends read Ghostty's terminal state. Font availability and browser capabilities can change appearance. Measure the workload on the backend your users will run. The [benchmark report](https://ghostty.shaulavo.dev/docs/concepts/benchmarks/) keeps renderer comparisons and limitations together.

## If it doesn't work

### WebGPU is unavailable

Use a secure context and a current browser with a usable GPU adapter. The main entry falls back automatically. A worker operation may return a capability error. Keep its `code`, `why`, and `fix` when displaying it to the user.

### Many terminals lose WebGL contexts

Browsers impose context limits. Dispose terminals you remove and bound the number of simultaneously live terminals. Test your intended count on your target browser. The main entry follows the remaining backend order after context loss, including hardware WebGPU when Linux selected WebGL2 first.
