You will open a terminal whose emulator, frame building and GPU rendering run in a dedicated worker. Start with a bundler that supports worker URLs, OffscreenCanvas and a supported GPU backend.

## When to use it

Pick the worker entry when many terminals receive dense output at the same time, or when the page thread must stay free for your app. Terminals parse and draw off the page thread, so one terminal's write is not queued behind the page's work. With many terminals, share workers through a pool (step 4). The main entry parses every terminal on the page thread. That uses the least total CPU, but sixteen terminals each redrawing a full truecolor screen need more than one 60 Hz frame of page-thread time, so updates arrive late.

Call `mountWorker(host, fontUrl)` with an absolute font URL reachable by the worker. Fonts loaded through the page's `document.fonts` belong to the page. Supply the worker's font faces through `fonts`, using a URL or `Uint8Array` bytes.

## 2. Serve the assets

Keep `ghostty-vt.wasm`, `bridge.wasm` and the built worker alongside the package output. Defaults resolve them relative to the package module. For a custom deployment, set `assets: { wasm, bridge }` and `workerUrl` to the hosted URLs.

Your CSP must allow the worker URL in `worker-src`, WebAssembly compilation, and asset/font requests. Keep cross-origin assets under your CORS policy. This worker uses messages; shared memory and cross-origin isolation are unnecessary for this path.

## 3. Await native operations

The main entry updates native state synchronously. Worker writes, reads, appearance changes and disposal return promises. Await a write before a read that depends on it. Host operations such as `focus` keep their synchronous shape.

The worker's `backend` accepts `auto`, `webgpu` and `webgl`. Its current API has capability limits for Canvas modes, link providers, keyboard link discovery and finite synchronous input connections. `attachTerminalHotkeys` is an optional `ghostty-webgpu/hotkeys` add-on for the synchronous main-thread terminal. Keep those boundaries in mind when migrating an interactive host.

## 4. Share workers between many terminals

Pass one `TerminalWorkerPool` to every `Terminal.create` call when a page shows several busy terminals. The pool starts a worker per terminal up to its `workers` limit, half the logical cores and at most four by default, then puts each further terminal on the least loaded worker. Only terminals with the same worker URL and the same `fonts` share a worker. Terminals on one worker share its GPU device, glyph atlas and font faces, and paint as soon as their written output is parsed instead of waiting for the next display frame; output from an attached producer port still paints at the next display frame. That costs less CPU and memory than one worker per terminal and answers writes sooner. A worker stops when its last terminal is disposed.

## If it doesn't work

### The font or worker request returns 404

Inspect the deployed asset URLs. A nested site base path changes document-relative URLs. Prefer URLs resolved by the bundler or absolute URLs you supply explicitly.

### A call returns a capability error

Read the error's `why` and `fix`. Use the main entry when your integration needs a synchronous original-input handler or a currently unsupported worker capability.
