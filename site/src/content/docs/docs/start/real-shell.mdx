Notice how the protocol splits data and control across WebSocket frame types:

- **Binary frames** carry raw terminal bytes in both directions: PTY output goes directly into `terminal.write(new Uint8Array(data))`, and browser keystrokes from `terminal.onData(({ bytes }) => ...)` go straight back to the PTY.
- **Text frames** carry JSON resize messages (`{ type: 'resize', columns, rows }`). Because `await terminal.open(host)` fits the grid before resolving, `terminal.geometry()` already holds the true dimensions the instant the socket opens.

<Aside type='caution' title='Pitfall: mixed content with ws://'>
  Pages served over `https://` cannot open insecure `ws://` sockets. Run this tutorial from a local
  `http://localhost` or `http://127.0.0.1` dev server, and terminate TLS (`wss://`) in front of any
  deployed PTY endpoint.
</Aside>

## Verify bytes and resize sync

1. Click the terminal, type `printf 'Hello from Bash\n'`, and press Enter to confirm round-trip byte delivery.
2. Resize the browser window and run `stty size`. The printed rows and columns should match `terminal.geometry()`.

<details class='deep-dive'>
  <summary>Why bytes never pass through TextDecoder</summary>
  <div class='deep-dive__body'>
    <p>
      A PTY can split a multi-byte UTF-8 character or an escape sequence across two separate OS
      reads and two separate WebSocket frames. Decoding each chunk independently to a JavaScript
      string corrupts split sequences with replacement characters (<code>U+FFFD</code>) and burns
      extra UTF-16 allocation overhead.
    </p>
    <p>
      Feeding raw <code>Uint8Array</code> chunks directly to <code>terminal.write()</code> lets{' '}
      <code>libghostty-vt</code>'s stateful UTF-8 and VT parser stitch split sequences natively.
    </p>
  </div>
</details>

## Security checklist before deploying

The example server above is scoped for localhost development: it binds only to `127.0.0.1`, rejects non-loopback `Origin` headers, validates integer grid bounds (`1..500` columns and `1..200` rows), and closes sockets on malformed JSON.

Because a PTY spawns a shell with the host user's permissions, put these controls in place before exposing any PTY endpoint on a network:

- Require authentication on the WebSocket upgrade request and enforce an explicit `Origin` allowlist.
- Isolate each user's shell inside a container, sandbox, or dedicated OS account.
- Cap concurrent connections per user and bound outbound buffers when a client stops reading (see [Wire a PTY](https://ghostty.shaulavo.dev/docs/guides/pty/) for backpressure patterns).

<div class='recap-card'>
  <p class='recap-card__title'>Recap</p>
  <ul>
    <li>
      Use binary WebSocket frames (`socket.binaryType = 'arraybuffer'`) for raw PTY bytes and text
      frames for JSON resize control messages.
    </li>
    <li>
      Read `terminal.geometry()` immediately after `await terminal.open(host)` to send the initial
      PTY size.
    </li>
    <li>
      Keep `terminal.onResize` wired to the socket so interactive TUIs reflow cleanly when the
      viewport changes.
    </li>
    <li>
      Never expose a shell WebSocket beyond `127.0.0.1` without authentication, origin checks, and
      OS/container isolation.
    </li>
  </ul>
