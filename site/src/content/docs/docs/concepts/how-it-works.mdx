`ghostty-webgpu` keeps all terminal semantics inside Ghostty's `libghostty-vt` compiled to WebAssembly without downstream patches. The TypeScript layer owns browser integration: layout measurement, keyboard and pointer input, font rasterization, and GPU/Canvas/DOM submission.

```text
PTY bytes -> libghostty-vt (ghostty-vt.wasm) -> native screen, modes, scrollback
                                                       |
                                           render-state damage flags
                                                       |
                           +---------------------------+---------------------------+
                           v                                                       v
               Zig frame builder (bridge.wasm)                       Direct row reader
               persistent cell & glyph records                    (Canvas 2D / DOM surface)
                           |
                           v
                  WebGPU / WebGL2
```

## One authoritative terminal state

Every escape sequence, wrapping rule, reflow step, selection coordinate, and Unicode width comes from `libghostty-vt`. Four layers expose that state at increasing levels of browser integration:

1. `GhosttyRuntime` (`ghostty-webgpu/core`): loads and instantiates `ghostty-vt.wasm` and `bridge.wasm` in browser or Node with no DOM globals.
2. `GhosttyTerminal` (`ghostty-webgpu/core`): headless terminal instance for writing bytes, resizing, reading lines, and querying geometry.
3. `TerminalSession` (`ghostty-webgpu/core`): adds appearance management, selection history, mouse/key encoding, links, and typed events.
4. `Terminal` (`ghostty-webgpu` or `ghostty-webgpu/worker`): mounts the DOM host, fits the container synchronously on `open()`, drives focus/IME/pointer/scrollbar/accessibility, and attaches a renderer.

Because every renderer and every query (`readLines`, `getSelection`, accessibility text) reads the same native state, switching from Canvas 2D to WebGPU during startup or recovering from a lost GPU device never loses screen contents.

The checked-in WASM binary is built from the exact upstream Ghostty commit, Zig compiler version, and hashes recorded in [ghostty-vt.provenance.json](https://github.com/ShaulLavo/ghostty-webgpu/blob/main/ghostty-vt.provenance.json). [ADR 001](https://github.com/ShaulLavo/ghostty-webgpu/blob/main/docs/adr/001-unpatched-pinned-ghostty-core.md) documents why the core stays unpatched.

## Main thread vs. worker boundary

- **Main entry (`ghostty-webgpu`):** after async `Terminal.create()` and `open()`, native mutations (`write`, `resize`, `setTheme`, `readLines`) execute synchronously on the page thread. During `open()`, `TerminalHost` computes the initial fit before constructing the renderer so frame one paints at the container's true dimensions.
- **Worker entry (`ghostty-webgpu/worker`):** runs `libghostty-vt`, `bridge.wasm`, and the WebGPU or WebGL2 renderer inside a dedicated worker (or `TerminalWorkerPool`) bound to an `OffscreenCanvas`. The page sends layout updates and input events over `MessagePort`; the worker sends back compact text-row deltas only for rows whose characters changed.

## Live state vs. submitted frames

`terminal.write()` parses bytes into `libghostty-vt` immediately, while rendering is coalesced onto the scheduler's frame boundary (unless `presentation: 'immediate'` is set).

- Call `readLines()` when you want the exact emulator buffer right now.
- Read `visibleLines()`, `submittedFrame`, or subscribe to `onFrame` / `onText` when you want the coherent frame last presented to the user.
