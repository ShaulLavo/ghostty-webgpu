## Findings that change the decision

1. Keep our unpatched core plus separate bridge as the text baseline. Coder's packed API is coarser than NimbleMarkets' new C-API adapter, but its actual Canvas caller repeatedly extracts the entire viewport through `getLine`. NimbleMarkets' GPU renderers fix that repeated viewport fetch, then pay many JS/WASM calls per cell and upload the complete packed grid on every painted frame. Our bridge reads the public API inside WASM and retains changed cell/glyph ranges. This is an architectural comparison, not a new speed measurement. ## Coder baseline, end to end

### Host, ownership and write path

`Ghostty` loads and instantiates the terminal WASM and creates a `GhosttyTerminal`. `Terminal.open` creates DOM/canvas/input/selection/link machinery and a `CanvasRenderer`. The low-level terminal owns the opaque handle, the shared WASM memory reference, a reusable viewport output allocation and a pool of JS cell objects. A `Ghostty` instance can create multiple terminal handles, but the browser host/render work is still ordinary main-thread JS. [src coder/ghostty-web@1858a59 lib/ghostty.ts:1] [src coder/ghostty-web@1858a59 lib/ghostty.ts:254] [src coder/ghostty-web@1858a59 lib/terminal.ts:421]

`Terminal.write` forwards immediately to native parsing, processes response bytes through `onData`, invalidates links, manages scroll-to-bottom and scans bytes/strings for bell/title handling. Low-level string input is UTF-8 encoded; either input form is copied into a fresh WASM allocation with `.set`, parsed synchronously, then freed. This is not a write queue providing backpressure. The resize-only queue is a different path. [src coder/ghostty-web@1858a59 lib/terminal.ts:543] [src coder/ghostty-web@1858a59 lib/terminal.ts:557] [src coder/ghostty-web@1858a59 lib/terminal.ts:1158] [src coder/ghostty-web@1858a59 lib/ghostty.ts:342]

The patch's `TerminalWrapper` embeds Ghostty `Terminal`, a custom `ResponseHandler`/stream, `RenderState`, a response buffer and alternate-screen tracking. This is more invasive than a helper that adds bulk getters: it owns terminal setup and dispatches VT operations itself. The handler directly handles modes, screen switching, cursor styles, queries and keyboard protocol state, with ignored operations in its switch. [src coder/ghostty-web@1858a59 patches/ghostty-wasm-api.patch:480] [src coder/ghostty-web@1858a59 patches/ghostty-wasm-api.patch:538] [src coder/ghostty-web@1858a59 patches/ghostty-wasm-api.patch:759]

### Core and bridge API granularity

The custom `GhosttyCell` is 16 bytes: codepoint, resolved RGB foreground/background, eight style bits, width, a u16 hyperlink indicator, grapheme extra-count and padding. The nominal hyperlink ID is written as 1/0, not a unique link identifier. Distinct underline styles collapse into a single bit. Grapheme codepoints and URI bytes require separate lookups. [src coder/ghostty-web@1858a59 patches/ghostty-wasm-api.patch:773] [src coder/ghostty-web@1858a59 patches/ghostty-wasm-api.patch:1107] [src coder/ghostty-web@1858a59 patches/ghostty-wasm-api.patch:1138]

`update` refreshes the internal `RenderState`; scalar cursor/colors/global damage and per-row damage are separate exports. `getViewport` is one bulk call writing every visible cell into the reusable output allocation, then JS reads it into its cell pool. That is coarse API granularity, not zero-copy: each cell is repacked in WASM and unpacked into a JS object. [src coder/ghostty-web@1858a59 lib/ghostty.ts:384] [src coder/ghostty-web@1858a59 lib/ghostty.ts:446] [src coder/ghostty-web@1858a59 lib/ghostty.ts:770]

The packed exporter bypasses the RenderState's cached cell data and traverses active screen page pins, resolving styles and grapheme counts again. `RenderState.update` has already copied changed raw row cells and duplicated managed graphemes/styles into its own snapshot. Thus the packed exporter duplicates work with an internal snapshot, rather than exposing that snapshot directly. [src coder/ghostty-web@1858a59 patches/ghostty-wasm-api.patch:1025] [src coder/ghostty-web@1858a59 patches/ghostty-wasm-api.patch:1091] [src ghostty-org/ghostty@5714ed0 src/terminal/render.zig:490]

### Actual frame construction and copies

For an active-screen painted row the path is:

```text
core pages
  → RenderState update, changed-row raw copy + managed data
  → getLine(y)
      → update again
      → getViewport(): pack ALL rows × cols into WASM scratch, 16 bytes/cell
      → parseCellsIntoPool(): rewrite ALL pooled JS cell fields
      → viewport.slice(row) + clone each row cell into new objects
  → CanvasRenderer backgrounds, then fillText per nonempty cell
      → extra grapheme lookup for multi-codepoint cells
```

Every arrow above is source-traced; the WASM typed-array/DataView creation itself is a borrowed view, while packing, field writes, row clones and grapheme `Array.from` are real materialization/copy steps. [src coder/ghostty-web@1858a59 lib/ghostty.ts:446] [src coder/ghostty-web@1858a59 lib/ghostty.ts:482] [src coder/ghostty-web@1858a59 lib/ghostty.ts:770] [src coder/ghostty-web@1858a59 lib/ghostty.ts:802] [src coder/ghostty-web@1858a59 lib/renderer.ts:444]

If C columns and R active rows all redraw, `render` calls `getLine` R times, so the exporter and JS cell-pool decode process R²C cells, before any extra cursor/hover reads. This is a source-derived operation count, not timing. At 200×50, a full redraw entails 50 exports of 10,000 cells, 8,000,000 bytes written into the packed WASM output across those calls and 500,000 pool-cell decodes, plus 10,000 returned row objects. It does not mean an 8 MB IPC transfer: the output lives in one reusable WASM allocation. [src coder/ghostty-web@1858a59 lib/renderer.ts:444] [src coder/ghostty-web@1858a59 lib/ghostty.ts:482] [measured: arithmetic R × (R × C), 16-byte cell size from those sources]

### Dirty rows, scrolling and glyphs

The renderer uses native row dirtiness plus selection and hovered-link rows. It expands damage to adjacent rows for tall/overflowing glyphs. For a scrolled viewport, every row is considered needing paint; history rows use a separate per-line scrollback exporter and active rows still use the expensive `getLine`. There is no GPU retained row ring or Canvas pixel scrolling reuse in this renderer path. [src coder/ghostty-web@1858a59 lib/renderer.ts:424] [src coder/ghostty-web@1858a59 lib/renderer.ts:452] [src coder/ghostty-web@1858a59 lib/ghostty.ts:549]

Each line paints backgrounds first and text afterward to avoid clipping neighboring grapheme overhangs. Text goes through the browser's `fillText`, one terminal cell/grapheme string at a time; extra codepoints are obtained from a reusable 16-u32 scratch allocation then copied to a JS array/string. This can shape within a grapheme, but is not native Ghostty shaping or a shaping run across arbitrary cells. It has no text atlas in this baseline. [src coder/ghostty-web@1858a59 lib/renderer.ts:514] [src coder/ghostty-web@1858a59 lib/renderer.ts:637] [src coder/ghostty-web@1858a59 lib/ghostty.ts:802] [hypothesis: cross-cell shaping limitation]

### Scheduling and integration limits

Main uses a perpetual RAF loop and invokes the renderer plus a cursor read even when idle. Blink has its own interval. Coder recently added direct rendering when an awaited echo arrives, but that does not replace the RAF loop. Named-buffer consumption is synchronous and instance-global. A small WASM trampoline places JS-callable wrappers in the core function table. The complete relevant copy chain is:

```text
producer's Go pixels
  → JS Uint8Array via CopyBytesToJS                  [L6]
  → registry entry, reference only                   [L6]
  → terminal WASM allocator buffer via .set           [this lane]
  → LoadingImage.data.appendSlice, then free scratch  [this lane]
  → decode/normalize if compressed or PNG             [format-dependent]
  → renderer format conversion/cache and GPU upload   [backend-dependent]
```
