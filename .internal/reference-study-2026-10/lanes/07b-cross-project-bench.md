# L7b: cross-project terminal benchmarks

Status: partial. Experimental measurements and local adapters are complete; Wraithterm/NimbleMarkets WebGPU and corrected-layout reruns are blocked by fresh hardware-context creation failures. No headline speed, physical display latency, or energy claim.

## Findings so far

- A smaller GPU record is not enough to predict end-to-end speed. The clean matched-font/geometry group of our WebGPU, our WebGL2, and xterm WebGL2 shows much lower CPU for our WebGL2 on repeated ASCII/cursor chunks, while sustained logs narrow the difference. GPU API/driver cost is part of these CPU totals. [measured: `../bench/L7b/matrix-1/results.json`, 4 counterbalanced repetitions per entry, 80x24/DPR2/120 paced updates]
- Native parser throughput is a separate advantage in these fixtures; SGR narrows it. Parsing excludes painting, source setup, input construction, and screen extraction. The implementations use different Ghostty revisions and JS/wasm bindings, so this does not isolate a compiler or boundary-overhead cause. [measured: `../bench/L7b/parser-1/results.json`, 16MiB per fixture, 4 repetitions, full-screen qualification]
- Restty's native WebGPU/WebGL2 runtime is built and passes the text spot check. Its font/raster/row-height path differs, so cross-project timings remain exploratory. [measured: `../bench/L7b/restty-smoke-2/results.json`, `matrix-1/results.json`]
- Wraithterm was added by coordinator steering and is now the next complete-terminal candidate. Beamterm is renderer-only with the same headless Ghostty core used for its control. NimbleMarkets nm-webgpu's pinned Ghostty source built successfully with Zig0.15.2. The later GPU creation block prevents a rendering verdict. [measured: L7b build commands and lane-owned artifacts; `../bench/L7b/beam-smoke-2/results.json`]

## Methodology and limits

The scripts reuse `bench/comparison-entry.ts`, its fixtures, exact pinned font assets, expected-screen parser validation, and `scripts/comparison-guards.mjs` process counters. A small directed runner avoids the stock runner's failed element-screenshot prerequisite. Each measurement takes `/work/tmp/quiet-turn.sh`, the installed heavy runner, and NVIDIA idle/window gates. Four repetitions use forward/reverse/forward/reverse arm order. Inputs are prepared before timing, delivered as matching UTF-8 chunks, and pages are recreated between arms. [measured: `../bench/L7b/protocol*.md`, `scripts/study-run.mjs` retained with final reproducer]

Hardware is PC i7-14700K, RTX3060Ti, NVIDIA615.78.08, Chromium153.0.8010.12, headed native Wayland, default ANGLE OpenGL. WebGPU separately reports a hardware NVIDIA adapter. No cross-host comparisons. The Mac was reachable/on AC but loaded, so it was not selected. [measured: `../bench/L7a/mac-before.txt`, `../bench/L7b/*/results.json` environment plus observed `/proc` browser argv]

Counters include all browser processes, with renderer and GPU CPU shown separately. Percentages use one CPU core as100%, not the whole20-core machine. CDP counters have coarse CPU ticks; one-second idle values near0..2% are a resolution-limited observation. Main-realm JS heap excludes worker heaps, GPU allocations and wasm memory. Paced frame intervals are not physical presentation or maximum throughput. [src ShaulLavo/ghostty-webgpu@26d3891 scripts/comparison-guards.mjs:122; measured: `../bench/L7b/*/results.json`, `cpu.tickSeconds=0.01`]

Fairness details found before timings:

- Same12px font request and exact regular/bold files produce different native cell rounding/line metrics. At80x24/DPR2 oursGPU/GL and xterm have1120x912 backings, coderCanvas1280x672, Restty1120x768. The first group is the strict geometry group. Coder/Restty have no equivalent public line-height option, and timing them does not isolate the backend. [measured: `../bench/L7b/restty-smoke-2/results.json`, `info.canvases`]
- Initial80x24 section height370 clips the bottom of the native canvas. The GPU still builds the full backing grid, but that matrix is preliminary rather than whole-visible-screen evidence. L6 uses100x30, section760x600 and viewport3200x2560 to fit16 active terminals. [measured: initial bundle HTML, L6 bundle HTML/settings and runner viewport]
- Scrollback is10000lines where available; native also gets64MiB byte budget, legacy coder64MiB, Restty64MiB. Native comparison entry shares one runtime, coder shares one runtime, Restty adapter currently uses one isolated session per terminal for reliable core-handle capture. Multi-terminal ownership differs and must be included in architectural interpretation. [src ShaulLavo/ghostty-webgpu@26d3891 bench/comparison-entry.ts:112; measured: lane adapters]
- Latin-only primary font does not establish Unicode visual equivalence. Restty/Wraith require supplied fallback fonts; browser Canvas may choose system fallbacks. Unicode performance is withheld wherever visible work differs. [src wiedymi/restty@3db45b0 src/runtime/core/config.ts:80; src betterclever/wraithterm@1151069 packages/wraith/src/index.ts:216; measured: full-resolution smoke screenshots]

## Correctness and visual checks

All completed `matrix-1` and `L6-one` per-workload texts agree across projects and repetitions after removing trailing U+0020 padding only. Leading/interior spaces, Unicode and row boundaries remain intact. Each multi-terminal result also checks that all terminal texts agree. The raw text hash groups are in `matrix-1-equivalence.json` and `L6-one-equivalence.json`; `analyze.py` regenerates them. Initial hash groups differed only because our `visibleLines()` preserves right padding and the counterpart helpers trim it. [measured: `../bench/L7b/*-equivalence.json`, raw `texts` arrays]

The ntcharts heatmap consists of colored background cells, so text agreement alone would be weak. Unscaled crop checks found1596000/1596000 non-black pixels in each1400x1140 native/xterm crop. Our WebGPU, WebGL2 and Canvas2D crops have identical decoded pixelSHA256 `a6582a38dc7eb292c434e49b284846b3705fa0f8955b95faa233a8725f26b5e0`. Xterm uses more color values and differs in pixels, so the result establishes equivalent painted content rather than pixel identity across all projects. Coder and Restty crop geometry differs as disclosed above; all have substantial painted coverage. [measured: `../bench/L7b/pixels/checks.json`, full-resolution PNGs and `scripts/study-pixels.mjs`]

Qualification found two actual counterpart limits:

- `ghostty-web@0.4.0` accepts35 repeated4110-byte ASCII writes but its documented terminal API crashes the isolated renderer process on the13th ZWJ-heavy Unicode write. Both empty-write APIs reject with `RangeError: offset is out of bounds`. Those diagnostic failures are preserved and are not counted as fast work. [measured: `../bench/L7b/base-smoke/comparison.json`, `legacyWriteControl`, `originalUnicodeProbe`, `emptyWriteProbe`]
- Xterm6.0.0 loses ZWJ joiners on the one-byte Unicode parser path, where the expected woman-technologist/family sequences become unjoined scalars. The normal4KiB comparison path is separate. No Unicode speed ranking uses the failing1-byte path. [measured: `../bench/L7b/base-smoke/comparison.json`, xterm `parserErrors`]

The initial L6 native-WebGPU qualifier reads last-submitted text after twoRAF callbacks. It passed once and failed three times. The lane now waits for the expected submitted text, bounded at120frames and outside timing, rather than assuming two callbacks imply completion. This is a measurement qualification change, not proof that a product rendering bug was fixed. [measured: `../bench/L7b/L6-one/results.json`; lane-local `correctness()`]

## Wraithterm and NimbleMarkets execution block

Wraith's adapter uses native `Wraith.mount`, not its xterm wrapper. It compiles the checked-in SDK/worker sources and uses the checked-in2.7MiB engine. The exact primary WOFF2 is losslessly converted toSFNT through fonttools so Rust and browser consume the same outlines. The shim requests the native control's fitted pixel row height through Wraith's public line-height option. Runtime geometry could not be qualified because initialization failed before `ready`. [src betterclever/wraithterm@1151069 packages/wraith/src/index.ts:209; crates/wraith-engine/src/text.rs:243; measured: `../bench/L7b/build-wraith-study.sh`, `bundle-wraith/`, `wraith-smoke/results.json`]

Both Wraith and our native WebGPU control fail `GPUAdapter.requestDevice` with `vkCreateDevice failed with VK_ERROR_INITIALIZATION_FAILED` in a fresh browser. A separate fresh-browser native-only control fails as well. The attempted measurement window was stopped after setup failure. This prevents a Wraith speed conclusion. [measured: `../bench/L7b/wraith-smoke/results.json`, `webgpu-control/results.json`, `wraith-one/results.json`]

At the failure, `nvidia-smi` reports7824/8192MiB used,0%GPUutilization; HyprlandPID2752 accounts for6961MiB and quickshell308MiB. This remains after lane browser processes close. VRAM pressure is a plausible cause, not a proven diagnosis of the device-creation error. The desktop was not restarted or reconfigured. Mac was rechecked, onAC and unreserved, but load21.9/19.0/17.1 made it unsuitable for a quiet CPU comparison. [measured: `../bench/L7b/gpu-after-pressure.txt`, `mac-late.txt`; hypothesis: cause of Vulkan initialization failure]

NimbleMarkets nm-webgpu builds its pinned Ghostty6590196 with the branch patch and Zig0.15.2. The branch script ignores the `ZIG` environment override, so the first attempt used system0.17 and correctly failed the required-version check. The pinned compiler build then exposed its own untracked `zig-pkg/` cache guard. Running the same patch/build/reverse-patch steps in the isolated owned worktree succeeded and produced a611KiB wasm. No source patch was rewritten. A WebGPU benchmark must wait for the common control to initialize successfully; this lane does not substitute its WebGL sibling and call it the requested WebGPU result. [measured: `../bench/L7b/build-nm*.sh`, heavy runner receipts; src NimbleMarkets/ghostty-web@bfbe0e5 scripts/build-wasm.sh:6]

The resolving experiment is concrete: take a headed hardware session with sufficient freeVRAM, run the retained native-only smoke first, then run `wraith-native` against native WebGPU/WebGL2/xterm using the same L6chunks and fitted geometry. A quiet M1 session is an alternative, measured as its own cohort. Wraith's compact20-byte cells/row map and native harfrust/swash pipeline remain strong candidates; these source properties have not received an independent speed verdict here. ## What is real, and what remains noise

- Large isolated parser gaps are real in this bounded experiment: nativeASCII510MiB/s versus xterm143 and coder101, native logs630 versus123/106, with non-overlapping observed four-run ranges. Restty's334/349 lies between. SGR narrows the gap to native117 versus Restty109/xterm102; cursor native/Restty ranges overlap. These measure whole parser-entry pipelines with different core revisions, not only the parser algorithm. [measured: parser table and `parser-1/results.json`]
- In the preliminary matched-backing native/xterm group, nativeGL's ASCII/SGR/cursor CPU reduction is large and consistent. NativeWebGPU and xterm logging ranges overlap; there is no supported general winner there. Repeated chunks can produce identical viewport records, allowing ourGL to skip uploads/draws. That is useful redundant-work avoidance, but the sustained-logs and heatmap workloads are the better product evidence. [src ShaulLavo/ghostty-webgpu@26d3891 src/render/webgl/renderer.ts:424; measured: `matrix-1/results.json`]

[measured: L6 raw results, exclusions, heavy overlap]
- Beamterm's roughly0.6..0.7ms dense/scroll cell-conversion component is larger than the timer quantum and persists across runs. That is a measured cost of this public JS adapter. It does not establish an intrinsic GPU-renderer disadvantage. [measured: `beam-warm/results.json`]

## What the results say about each architecture

1. **Xterm:** its JS parser entry is slower on theseASCII/log fixtures, but its WebGL renderer is competitive on a dense realTUI at one terminal. Separating parsing from painting prevents the parser result becoming an unjustified renderer judgment. Its asynchronous write queue has higher acknowledgement time than the synchronous APIs; compare complete update endpoints rather than callback return alone. [src ShaulLavo/ghostty-webgpu@26d3891 bench/comparison-entry.ts:416; measured: parser, L6, acknowledgement tables]
2. **CoderCanvas:** the measured API write can return quickly while later painting consumes much moreCPU under dense output. Lower wasm-boundary call cost would not automatically remove row extraction/Canvas work. Its historical container clipping and repeated Unicode crash prevent a broad speed/quality claim. [measured: L6 CPU/acks, smoke crash, pixel checks; hypothesis: attribution to extraction/paint]
3. **Restty:** this is a genuine alternative font/render pipeline, not just another backend label. Its single-terminal measurements suggest more JS-side work here, but explicit-font shaping/rasterization and the unmatched display metrics are material confounders. Multi-terminal measurements use one isolated session per terminal to capture the right core handle, unlike its shared default session. They do not establish default Restty multi-terminal performance. [src wiedymi/restty@3db45b0 src/runtime/core/session.ts:11; src wiedymi/restty@3db45b0 src/runtime/create-runtime/render-tick-webgl-scene.ts:116; measured: lane adapter and results]
4. **Wraith:** no performance verdict. Native Rust font/frame construction, compact20-byte records and retained row mapping remain worth testing. A failure also seen in the fresh common control cannot reject its architecture. [src betterclever/wraithterm@1151069 crates/wraith-engine/src/retained.rs:26; measured: device-creation failures]
5. **Beamterm:** the measured cell-conversion boundary matters more than the small CPU submission call in this adapter. It is a renderer, not a byte-stream terminal, and this experiment must not appear in a complete-terminal ranking. [src junkdog/beamterm@7cde649 examples/terminal-emulator/Cargo.toml:14; measured: renderer stage table]
6. **NimbleMarkets:** only buildability is established. A successful611KiB core build says nothing about its full-grid JS construction/WebGPU cost. No sibling/fork benchmark is substituted for the requested branch. [measured: nm-build-receipt; src NimbleMarkets/ghostty-web@bfbe0e5 lib/renderer-webgpu.ts:920]

## Final layout/endpoint audit and gaps

The historical Restty shim used CSS width `cols*fontSize*0.6` and height `rows*fontSize*1.2`, then the runtime chose a different intrinsic cell metric. The resulting canvas was resampled in CSS. The coder100-column canvas was800CSSpx wide inside a760px section, clipping5columns, although its full backing grid still rendered. These are adapter-layout errors, not counterpart bugs. The final reproducer uses the actual Restty backing size divided byDPR and widens sections to820px with a3360px viewport.
