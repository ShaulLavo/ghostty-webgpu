## Decisions that matter most

1. A Ghostty bump does **not** unlock a new text-frame extraction architecture. Raw row views, row IDs, dirty-row iteration, multi-getters, UTF-8 grapheme reads, two-phase updates, overscan, selection, and tracked grid references already exist at the pin. Several are absent from our JS bindings. The cheapest upstream-based simplification needs no bump. [src ghostty-org/ghostty@7b11f3d include/ghostty/vt/render.h:460] [src ghostty-org/ghostty@7b11f3d include/ghostty/vt/render.h:668] [src ghostty-org/ghostty@7b11f3d include/ghostty/vt/render.h:838] [src ShaulLavo/ghostty-webgpu@26d3891 src/core/abi.ts:716]
2. HEAD mainly adds useful image placement work, semantic shell events, prompt scrolling, memory accounting, and richer stream stop boundaries. It leaves our renderer-specific bridge work intact. Images are low priority here, so this is not a compelling text-performance upgrade by itself. The priority judgment is [hypothesis]. 3. HEAD requires Zig 0.17.0. Our bridge still uses array repetition syntax removed in the upstream migration. A pin bump needs a toolchain/bridge/provenance update and qualification, not just a changed hash. Likely bounded mechanical work, but no build was attempted. [src ghostty-org/ghostty@68640f3 build.zig.zon:6] [src ShaulLavo/ghostty-webgpu@26d3891 scripts/bridge.zig:230] [hypothesis]
4. The current pin already documents how embedders must honor synchronized output. Our render-state update and renderer paths do not appear to implement that hold contract. Treat this as a concrete source finding awaiting a browser reproduction, not a proven screenshot failure. 5. "Native-like" needs five separate promises. We already run native VT logic. We do not run Ghostty's procedural sprites, native shaping, native rasterizers, or renderer implementation. Reusing each has a different cost, and HarfBuzz alone does not solve the other four. 6. xterm.js's strongest lessons are responsiveness under queued input, per-terminal visibility, procedural glyphs, and optional joined runs. Its WebGL model is incremental, but its glyph upload still compacts the whole visible model each frame. Our sparse uploads and WebGPU row indirection are worth retaining. ### Does a pin bump look cheap?

**For text rendering, its payoff looks small; its implementation cost looks moderate and mechanical.** The text API is largely the same. HEAD's minimum compiler is 0.17.0; the upstream migration changes builtin names, type-info representation, optimize enum spellings, and array repetition. Our bridge uses `**`, and our reproducibility manifest pins compiler bytes as well as source/archive/artifact hashes. The build recipe and all bridge inputs must be rebuilt and re-recorded together. This is not a fork rebase, but it is not a hash-only upgrade. [src ghostty-org/ghostty@68640f3 build.zig.zon:6] [src ghostty-org/ghostty@68640f3 src/terminal/c/style.zig:31] [src ShaulLavo/ghostty-webgpu@26d3891 scripts/bridge.zig:230] [src ShaulLavo/ghostty-webgpu@26d3891 ghostty-vt.provenance.json:21] [hypothesis: cost/payoff]

Our current TS interface does not bind `vt_write_until_ground`, so its replacement is not a directly observed caller break here. New types/enums would still need binding/manifest verification when adopted. Prefer a narrow current-pin cleanup first; upgrade for semantic events, memory accounting, fixes, or image needs on their own merits.
