## Decision-relevant findings

- Go-booba is a useful replacement-compatibility target. It runs Go/Bubble Tea in browser WASM **and** connects to native PTY programs through WebSocket/WebTransport. Its browser bridge drains buffered output in bulk, but through copied strings and a 16 ms poll, not shared memory. Optimizing only our parser will not remove that producer-side latency. - NTCharts is principally a producer of terminal text/escapes, not a browser terminal implementation. Its current v2 branch already incorporates the older picture and v2-booba work. Treating those branches as three competing current renderers would misread the history. ## Go-booba

### Role, API and selected renderer

The Go top-level Run/NewProgram use native Bubble Tea under !js and delegate to the wasm package under js/wasm. The latter creates input/output syncBuffers and registers bubbletea_read/write/resize globals. The native server exposes a Session with PTY byte readers/writers and pixel-aware resize. It is both an in-browser Go TUI host and a remote terminal host. ### Copies and scheduling

WASM output is batched in a mutex-protected bytes.Buffer. ReadAndReset allocates a new byte slice and copies the buffer, then the JS callback returns string(data). The adapter polls every 16 ms and passes the resulting JS string to the terminal. Input Uint8Array is decoded to string in JS, then converted to []byte in Go. There is no SharedArrayBuffer, shared terminal memory view, zero-copy byte return or explicit producer backpressure in this bridge. The bulk path is one read of all accumulated bytes per poll. [src NimbleMarkets/go-booba@073c560 wasm/wasm.go:81] [src NimbleMarkets/go-booba@073c560 wasm/wasm.go:187] [src NimbleMarkets/go-booba@073c560 wasm/wasm.go:197] [src NimbleMarkets/go-booba@073c560 ts/adapter.ts:67] [src NimbleMarkets/go-booba@073c560 ts/adapter.ts:114]

WebSocket receives ArrayBuffers and creates a Uint8Array view before decoding the Sip message and forwarding the payload. Server output uses a fixed read buffer, runs every read through the Kitty transcoder and emits bounded binary messages. Thus binary transport does exist, but does not make the complete native-server path zero-copy. [src NimbleMarkets/go-booba@073c560 ts/websocket_adapter.ts:65] [src NimbleMarkets/go-booba@073c560 serve/handlers.go:76] [src NimbleMarkets/go-booba@073c560 serve/handlers.go:178] [src NimbleMarkets/go-booba@073c560 serve/kittygfx.go:65]

The NTCharts **image-only** named-buffer path is separate from booba's terminal writes. Browser Create allocates Go pixel bytes, fills RGBA, allocates a JS Uint8Array, copies with js.CopyBytesToJS and publishes it in globalThis.ghosttyKittySharedMemory. The pinned terminal looks up the name, allocates its own WASM memory, copies bytes again with .set, then deletes the registry entry. This avoids base64 payload transport/parse, but is neither same-memory access nor zero-copy. ### Stress and pain relevant to our API

- Truecolor is actively advertised to Go libraries through TERM_PROGRAM=ghostty, COLORTERM=truecolor and CLICOLOR_FORCE. The host carries arbitrary chart redraw bytes, mouse reporting, alternate screens and query replies. Actual chart interaction and v2 View flags are described below. Advertising Ghostty identity alone should not be mistaken for full native image capability. ## OpenTUI web, common main and indexzero branches

### Common architecture

The browser package wraps the vendored Zig OpenTUI OptimizedBuffer, exposing its memory and per-cell buffers. It has full and diff ANSI encoders implemented in WASM. Full encoding starts at home, optionally clears, emits changed SGR colors/attributes as it walks all cells, appends CRLF **after every row including the last**, and resets SGR. This bottom-row behavior is preserved in the capture and can cause scrolling in a terminal with exactly the grid dimensions. [src rbbydotdev/opentui-web@483099b packages/opentui-browser/src/buffer.ts:36] [src rbbydotdev/opentui-web@483099b packages/opentui/packages/core/src/zig/lib-wasm.zig:189] [src rbbydotdev/opentui-web@483099b packages/opentui/packages/core/src/zig/lib-wasm.zig:268]

The JS string encoder decodes the WASM scratch bytes. The bytes encoder allocates a fresh Uint8Array and copies bytes out of WASM; workers then transfer its ArrayBuffer. Direct-cell worker snapshots likewise copy chars, fg, bg and attributes into new transferable arrays. Transfers avoid an additional structured-clone payload copy; they do not eliminate the WASM-to-transfer-buffer copy or cell encoding.
