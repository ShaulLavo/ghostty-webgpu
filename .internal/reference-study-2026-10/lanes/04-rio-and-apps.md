# L4 — Rio and terminal applications/frontends

Source-level review at the revisions listed below; no repository was built or run. “Better” below means a concrete mechanism advantage, not a benchmark result. Performance changes are proposals to measure, not measured wins.

## Decision summary

1. **Keep our retained native frame builder and byte-range uploads.** Rio also rebuilds only dirty rows, but one changed row causes its WebGPU backend to upload the entire background buffer and concatenate/upload the entire foreground instance buffer. Our Zig builder emits changed cell/glyph ranges and the WebGPU pass uploads only those ranges. [src raphamorim/rio@ec9ca50 sugarloaf/src/grid/webgpu.rs:457] [src raphamorim/rio@ec9ca50 sugarloaf/src/grid/webgpu.rs:479] [src ShaulLavo/ghostty-webgpu@26d3891 src/render/webgpu/text-pass.ts:178]
2. **Keep our row-identity/rotation work.** Rio marks the whole viewport damaged on display scrolling and rebuilds every row; our bridge matches row IDs, detects rotation, and remaps physical rows in the shader. [src raphamorim/rio@ec9ca50 rio-vt/src/crosswords/mod.rs:689] [src ShaulLavo/ghostty-webgpu@26d3891 scripts/bridge.zig:310] [src ShaulLavo/ghostty-webgpu@26d3891 src/render/shaders/row-remap.wgsl.ts:1]
3. **Rio’s run shaping is the largest text-feature gap.** It shapes same-font/style runs with CoreText or swash and maps shaped glyphs back to cells; our native builder gives Canvas one cell/grapheme at a time, so cross-cell ligatures cannot form. Rio deliberately breaks some grid-hostile ligatures and at selection/cursor boundaries, a useful policy reference. [src raphamorim/rio@ec9ca50 rio-grid/src/lib.rs:13] [src raphamorim/rio@ec9ca50 rio-grid/src/lib.rs:1722] [src raphamorim/rio@ec9ca50 rio-grid/src/lib.rs:2192] [src ShaulLavo/ghostty-webgpu@26d3891 scripts/bridge.zig:617]
4. **Two GPU experiments are worth qualifying:** Rio’s fullscreen-triangle background pass and four-vertex glyph strips, versus our per-cell six-vertex background/glyph draws. These are different tradeoffs, not established wins; our ADR already requires evidence before replacing instancing. [src raphamorim/rio@ec9ca50 sugarloaf/src/grid/shaders/grid.wgsl:98] [src raphamorim/rio@ec9ca50 sugarloaf/src/grid/shaders/grid.wgsl:234] [src ShaulLavo/ghostty-webgpu@26d3891 src/render/webgpu/text-pass.ts:231] [src ShaulLavo/ghostty-webgpu@26d3891 docs/adr/002-keep-instanced-webgpu-renderer.md:12]
5. **Rio at HEAD is not a working complete browser terminal.** It has a current headless `librio-wasm` core API and browser-capable Sugarloaf code, but the old `frontends/wasm` is only a window/event demo, and the main `rioterm` target has unconditional native-only imports/dependencies. ### Cells → shaped runs → GPU instances

- `rio-grid` emits a compact 4-byte premultiplied `CellBg` per cell and a 32-byte `CellText` per shaped glyph or decoration. A cell can produce several foreground instances. Cursor position/colors live mostly in uniforms, with separate block/non-block cursor sprite slots. - The background shader draws one fullscreen triangle and looks up the cell from fragment coordinates. Text uses four-vertex triangle-strip instances, integer grid positions, atlas bearings, and `textureLoad`, sampling only the selected grayscale or color atlas. ### Shaping and font/glyph caches

- Non-macOS shaping uses swash `ShapeContext`; rasterization uses `ScaleContext`. macOS uses CoreText. Runs share font and shaping-relevant bold/italic flags and include attached combining codepoints; explicit cell-start tables map UTF-8 or UTF-16 shaping clusters back to terminal columns. - A 256×8 bucketed LRU caches shaped runs by a 64-bit hash only, without retaining text for collision checks; the source explicitly accepts a possible wrong-glyph frame. We should not copy that correctness tradeoff: our native glyph index compares full codepoint/style/brush keys. ### Atlas design and failure behavior

- Each wgpu panel gets one fixed 2048² R8 and one fixed 2048² RGBA8 atlas, about 20 MiB of texture storage before instance buffers. New glyphs upload immediately with `queue.write_texture`. [src raphamorim/rio@ec9ca50 sugarloaf/src/grid/webgpu.rs:19] [src raphamorim/rio@ec9ca50 sugarloaf/src/grid/webgpu.rs:60] [src raphamorim/rio@ec9ca50 sugarloaf/src/grid/webgpu.rs:90]
- Allocation is shelf-based with one-pixel padding and a 10% acceptable vertical-waste test; there is no per-glyph free list. When full, the atlas is cleared and a full row rebuild repairs stale slots. [src raphamorim/rio@ec9ca50 sugarloaf/src/renderer/image_cache/atlas.rs:21] [src raphamorim/rio@ec9ca50 sugarloaf/src/grid/webgpu.rs:422] [src raphamorim/rio@ec9ca50 frontends/rioterm/src/screen/mod.rs:4492]
- Our atlas uses up to sixteen 512² layers per kind, LRU-recycles a whole layer, tracks row/page generations, and coalesces dirty rectangles for upload. That is better bounded eviction and avoids Rio’s whole-atlas invalidation, although both designs eagerly reserve roughly the same maximum GPU texture bytes per renderer/panel. [src ShaulLavo/ghostty-webgpu@26d3891 src/render/shared/atlas/atlas.ts:29] [src ShaulLavo/ghostty-webgpu@26d3891 src/render/shared/atlas/atlas.ts:292] [src ShaulLavo/ghostty-webgpu@26d3891 src/render/shared/atlas/atlas.ts:336] [src ShaulLavo/ghostty-webgpu@26d3891 src/render/webgpu/gpu-textures.ts:61]
- Rio’s `FRAMES_IN_FLIGHT = 3` arrays are not actually rotated in this wgpu implementation: writes, reads, and bind groups use slot zero, while the other buffers are allocated. This is retained complexity/memory, not a working triple-buffer advantage. [src raphamorim/rio@ec9ca50 sugarloaf/src/grid/webgpu.rs:19] [src raphamorim/rio@ec9ca50 sugarloaf/src/grid/webgpu.rs:165] [src raphamorim/rio@ec9ca50 sugarloaf/src/grid/webgpu.rs:340] [src raphamorim/rio@ec9ca50 sugarloaf/src/grid/webgpu.rs:452]

### Damage, row caching, uploads, and scrolling

- `TerminalDamage` is a coarse `Noop`/`Full`/`Partial`/`CursorOnly` gate; the snapshot’s row bits make the actual decision. `snapshot_visible` reuses destination row allocations, copies only dirty rows in partial frames, resolves style values, and refreshes referenced extras under the terminal lock. [src raphamorim/rio@ec9ca50 rio-vt/src/event/mod.rs:105] [src raphamorim/rio@ec9ca50 rio-vt/src/crosswords/mod.rs:2180] [src raphamorim/rio@ec9ca50 frontends/rioterm/src/context/renderable.rs:70]
- UI and PTY damage are merged once per panel under one terminal lock. Clean panels skip rendering, and `Noop`/`CursorOnly` frames preserve CPU/GPU cell data; cursor changes use uniforms/sprite slots rather than rebuilding text rows. - The important limitation is downstream: any background change uploads the whole `bg_cpu[0]`; any foreground/cursor change concatenates every retained row and uploads all foreground instances. Thus Rio’s row-level saving is CPU shaping/emission only, not partial GPU traffic. [src raphamorim/rio@ec9ca50 sugarloaf/src/grid/webgpu.rs:465] [src raphamorim/rio@ec9ca50 sugarloaf/src/grid/webgpu.rs:487]
- Our builder also has more complex reuse checks, but it returns per-row byte spans and has sparse/wrapped upload planners. - Display-offset changes call `mark_fully_damaged`; the full snapshot clones every visible row and the emit loop rebuilds all of them. There is no stable row-ID remap in Rio’s render path. - Our ring/row-ID path recognizes a pure rotation and can leave records resident while the shader changes row origin. This is better for scroll-heavy workloads and directly addresses Rio’s weakest path. ### Frame scheduling and backend selection

- Native event mode requests redraws and then waits; game mode polls continuously. The application comment and control flow show ordinary rendering paced by window-system redraw/vsync rather than an unconditional timer. [src raphamorim/rio@ec9ca50 frontends/rioterm/src/application.rs:2305]
- Per-route timers coalesce scheduled render and cursor events, and a present is skipped if no panel is dirty and no animation needs it. - Backend selection is compile-target/configuration driven, not our automatic hardware-WebGPU → WebGL2 → Canvas → DOM chain.
